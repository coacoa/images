GitHub ひとり運用チュートリアル
― プルリクエストと Actions を覚える

対象：git の push / pull はできるけど、プルリクエスト（PR）と GitHub Actions は未経験、という人向け。ひとりで使っているリポジトリで、そのまま練習できる構成にしてある。進捗（「できた」チェック）はこのブラウザに自動保存される（端末・ブラウザごとに別）。

進捗 0 / 14

各レッスン末尾の「できた」を押すとここに反映される。GitHub Pages に置けばスマホでも続きから復習できる。

Phase 0 ― 全体像

レッスン1：ソロでも PR と Actions が効く理由

ゴール：「PR はチーム開発のもの」という思い込みを外す。

ひとり運用でも、PR と Actions には実利がある。

  • PR = 変更の「検品工程」。main に直接 push すると、間違いは即公開される。ブランチ＋PR を挟むと、「差分を目で見る」「自動チェックを通す」という関所ができる。昨日の自分が今日の自分のレビュアーになる。
  • PR = 変更の履歴書。「なぜ変えたか」を PR の説明に書いておくと、半年後に git log を掘るより速く思い出せる。
  • Actions = 「push したら勝手にやってくれる作業」の置き場。たとえば君のメモサイトの make_index.sh。今は手元で回しているはずだけど、Actions に載せれば push するだけで index.html が自動生成・自動コミットされる（レッスン12 が本命）。

覚え方はひとつずつでいい。このチュートリアルの順番どおり、ブランチ → PR → 保護 → Actions 入門 → 実践（index 自動生成）と進めれば、必要なものだけ身につく。

やってみる：自分のリポジトリを1つ決める（メモサイトの images リポジトリが題材にちょうどいい）。以降の練習は全部そのリポジトリでやる。

レッスン2：用語の地図

ゴール：PR と Actions まわりの言葉を、自分の作業に結びつけて言える。
言葉意味（ひとことで）
ブランチ (branch)作業用の枝分かれ。main を汚さずに変更を育てる場所
プルリクエスト (PR)「このブランチを main に取り込んで」と頼むページ。差分レビューと自動チェックの場
マージ (merge)ブランチの変更を main に取り込むこと
スカッシュ (squash)ブランチの細かいコミットを1つに潰してからマージする方式。履歴がきれいになる
ブランチ保護 (branch protection)main への直接 push 禁止などのルールを課す仕組み
ワークフロー (workflow)Actions の定義ファイル。.github/workflows/*.yml に書く
トリガー (on:)ワークフローが動くきっかけ。push、PR、手動実行など
ジョブ (job) / ステップ (step)ジョブ＝作業の単位（仮想マシン1台分）。ステップ＝その中の1手順
ランナー (runner)ジョブを実行する仮想マシン。ubuntu-latest などと指定する

全部覚えなくていい。付録の早見表とフラッシュカードで後から引ける。

Phase 1 ― ブランチの基礎

レッスン3：ブランチを作って切り替える

ゴール：main から作業ブランチを切り、コミットして戻ってこられる。
# main を最新にしてから枝を切る
git switch main
git pull
git switch -c add-readme-line

# 何か1つ変更してコミット（例：README に1行足す）
git add .
git commit -m "README に1行追加"

# ブランチ一覧と現在地の確認
git branch

ブランチ名は add-readme-line のように「何をするか」が分かる短い名前がよい。work や test2 みたいな名前は後で困る。

やってみる：練習用ブランチを1つ切り、どうでもいい1行変更をコミットする。終わったら git switch main で戻り、その変更が main に入っていないことを確認する（ここがブランチの価値）。

レッスン4：差分を見る

ゴール：「何が変わるか」をマージ前に言葉で説明できる。
# 作業中の変更（まだコミット前）
git status
git diff

# ブランチが main とどう違うか（PR の差分と同じもの）
git diff main...HEAD

PR の「Files changed」タブに出るのは、最後の git diff main...HEAD と同じ内容。つまり PR のレビューは、手元でも先にできる。

やってみる：レッスン3 のブランチで git diff main...HEAD を実行し、自分の変更が過不足なく出るか見る。

Phase 2 ― 初めてのプルリクエスト

レッスン5：PR を作る

ゴール：ブランチを push して、PR ページを開く。
# ブランチを GitHub に送る（-u は初回だけ）
git push -u origin add-readme-line

push すると GitHub のリポジトリ画面に「Compare & pull request」というボタンが出る。それを押して PR を作る。ボタンが出ない場合は「Pull requests」タブ →「New pull request」からブランチを選ぶ。

  • タイトル：変更内容を1行で（例：「README に使い方を追記」）。
  • 説明：「何を・なぜ」を2〜3行。未来の自分へのメモだと思って書く。
  • base / compare の確認：base: main ← compare: add-readme-line の向きになっているか必ず見る。逆だと事故る。
やってみる：レッスン3 のブランチで PR を1つ作る。説明には「練習用 PR」と目的を書いておく。

レッスン6：セルフレビューとマージ

ゴール：自分の差分をレビューしてからマージし、後片付けまでやる。
  1. PR の 「Files changed」タブを開き、差分を最初から最後まで目で追う。自分が書いたつもりのない変更が混ざっていないか、ここで気づくのが PR の一番の効能。
  2. 気になる行には行コメントを残せる（自分宛のメモで OK）。
  3. 問題なければ 「Merge pull request」。マージ方式は3種類選べる：
    • Squash and merge（おすすめ）：ブランチの細かいコミットを1つに潰して main に入れる。ソロ運用の main はこれで十分きれいになる。
    • Create a merge commit：コミット履歴をそのまま残し、マージコミットを1つ追加。
    • Rebase and merge：コミットを main の先端に並べ替える。慣れてからでいい。
  4. マージ後は 「Delete branch」で GitHub 側のブランチを消す。手元でも片づける：
git switch main
git pull
git branch -d add-readme-line   # 手元のブランチも削除
やってみる：練習 PR をスカッシュでマージし、ブランチを両方（GitHub 側・手元）消す。main に変更が1コミットで入っていることを git log --oneline -3 で確認する。

Phase 3 ― PR 運用を固める

レッスン7：main を守る（ブランチ保護）

ゴール：「main へは PR 経由でしか入れない」を GitHub の仕組みで強制する。

意志の力に頼ると必ず直接 push する日が来る。仕組みで縛るのが正解。手順：リポジトリの Settings → Branches → Add classic branch protection rule で、Branch name pattern に main と入れ、次にチェックする：

  • Require a pull request before merging ― PR 経由を必須にする。ソロなら Required approvals は 0 でよい（自分で自分の PR を承認する儀式は不要）。
  • （レッスン11 の後で）Require status checks to pass before merging ― Actions のチェックが緑のときだけマージ可にする。

注意：保護を有効にすると、緊急時でも直接 push できなくなる。管理者にも適用するか（Do not allow bypassing）は最初は緩めでよい。「うっかり直接 push」を防げれば目的は達成。

やってみる：練習リポジトリに保護を設定し、わざと main に直接 push して拒否されることを確認する。これが正常動作。

レッスン8：gh CLI で PR を回す

ゴール：ブラウザを開かずに PR の作成・確認・マージができる。

GitHub 公式 CLI の gh を入れると、PR 操作がターミナルで完結する。NixOS なら gh パッケージを入れて gh auth login で認証するだけ。

# PR を作る（タイトルと本文をコミットから自動生成）
gh pr create --fill

# 自分の PR の状態を見る
gh pr status

# 差分をターミナルで見る
gh pr diff

# スカッシュでマージして、ブランチも消す
gh pr merge --squash --delete-branch

Doom Emacs やターミナル中心の生活なら、こちらの方が手に馴染むはず。ブラウザの PR 画面は「差分をじっくり見る」ときだけ開けばいい。

やってみる：次の練習 PR は gh pr create --fill から gh pr merge まで CLI だけで済ませる。

Phase 4 ― GitHub Actions 入門

レッスン9：ワークフロー YAML の骨格

ゴール：ワークフローファイルの3要素（on / jobs / steps）を読み解ける。

ワークフローは .github/workflows/ に置く YAML ファイル。骨格はこれだけ：

name: ワークフローの名前

on:            # いつ動くか（トリガー）
  push:

jobs:          # 何をするか
  job-name:
    runs-on: ubuntu-latest   # どの仮想マシンで
    steps:                   # 手順（上から順に実行）
      - run: echo "1つ目の手順"
      - uses: actions/checkout@v4   # 部品（アクション）を使う手順
  • run: はシェルコマンド。そのまま Ubuntu のターミナルだと思えばいい。bash / git / python などは最初から入っている。
  • uses: は誰かが作った部品の呼び出し。actions/checkout は「リポジトリのコードを仮想マシンに持ってくる」部品で、ほぼ全てのワークフローの最初に置く。
  • YAML はインデントが命。スペース2つずつ、タブ禁止。Actions の失敗原因の筆頭がこれ。

レッスン10：最初のワークフローを動かす

ゴール：手動実行でワークフローを走らせ、ログを読める。

最初は「push したら」ではなく手動実行で試すのが安全。workflow_dispatch というトリガーを付けると、GitHub の「Actions」タブからボタンで実行できる。

# .github/workflows/hello.yml
name: hello

on:
  workflow_dispatch:

jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello, Actions"
      - run: date; pwd; ls

これを main に置いて push すると、Actions タブに「hello」ワークフローが現れ、「Run workflow」ボタンから実行できる。実行結果（run）を開くと、ステップごとのログが読める。

料金の心配：公開リポジトリなら Actions は実質無料で使える（標準ランナー）。非公開でも月2,000分まで無料枠がある。練習で破産することはない。

やってみる：hello.yml を置いて手動実行し、ログで date の出力（UTC で表示されるはず）を確認する。ランナーの中身を uname -a や which nix で眺めてみるのも面白い。

Phase 5 ― PR × Actions

レッスン11：PR に自動チェックを付ける

ゴール：PR を開くたびに自動でチェックが走り、結果が PR 画面に付く状態にする。

トリガーを pull_request にすると、PR の作成・更新のたびにワークフローが走る。題材はメモサイト：make_index.sh がエラーなく走るか＋ <title> の無い HTML が混ざっていないか、を PR の時点で確かめる。

# .github/workflows/pr-check.yml
name: pr-check

on:
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: title の無い HTML を洗い出す
        run: |
          missing=$(grep -L '<title>' html/*.html || true)
          if [ -n "$missing" ]; then
            echo "title が無いファイル: $missing"
            exit 1
          fi

      - name: make_index.sh が動くか確認
        working-directory: html
        run: bash make_index.sh
  • チェックが成功すると PR に緑の ✓、失敗すると赤い × が付き、マージ前に気づける。
  • さらにレッスン7 のブランチ保護で Require status checks to pass before merging にこのチェックを指定すると、「緑でないとマージできない」まで強制できる。ここまで行くとソロでも立派な CI。
  • working-directory: はステップの実行場所。make_index.sh は html フォルダの中で回す前提のスクリプトだから、ここが大事（v2 の「カレントディレクトリの *.html を見る」仕様と一致）。
やってみる：わざと <title> の無い HTML を1つ足した PR を作り、チェックが赤くなることを確認してから、title を直して緑になるのを見る。

Phase 6 ― 実践（本命）：index.html の自動生成

レッスン12：push したら make_index.sh が走ってコミットまでされる

ゴール：メモを push するだけで index.html が自動で最新になる。手元でスクリプトを回す作業を卒業する。

レッスン11 のチェックと違い、こちらは「生成してコミットまでする」ワークフロー。完成形がこれ：

# .github/workflows/make-index.yml
name: make-index

on:
  push:
    branches: [main]
    paths:
      - 'html/*.html'
      - '!html/index.html'   # index.html 自身の変更では再実行しない（無限ループ防止）
  workflow_dispatch:          # 手動でも実行できるように

permissions:
  contents: write   # bot がコミットを push するために必要

jobs:
  index:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # 全履歴を持ってくる（理由は下）

      - name: index.html を生成
        working-directory: html
        run: bash make_index.sh

      - name: 変更があればコミットして push
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add html/index.html
          git diff --cached --quiet || git commit -m "index.html を自動生成"
          git push

大事なポイントは3つ：

  • fetch-depth: 0 ― make_index.sh v2 は日付に git log を使う。checkout の初期設定（fetch-depth: 1）は履歴が1件しか無いので、日付が全部おかしくなる。全履歴を持ってくるこの指定が必須。
  • paths の !html/index.html ― bot のコミット（index.html の変更）がまた push になって再実行…という無限ループを防ぐ。「対象に含める」指定の後ろに「ただしこれは除く」を書くのが GitHub の書法。
  • git diff --cached --quiet || ― 生成しても中身が変わらなかったらコミットしない。これでも二重の安全策になる。

前提の確認：この例は「リポジトリ直下に html フォルダがあり、その中に make_index.sh と *.html がいる」構成（coacoa.github.io/images/html/ の形）。フォルダ名が違う場合は paths と working-directory を実物に合わせて直すこと。

やってみる：このワークフロー自体も、レッスン5〜6 の作法どおりブランチ＋PR で入れる。マージ後、メモを1つ push して Actions タブで bot のコミットが自動で積まれるのを確認する。手元の make_index.sh 手回しは、ここで引退。

Phase 7 ― 運用と次の一歩

レッスン13：失敗したときの調べ方

ゴール：赤くなったワークフローを、ログから自力で直せる。
  1. Actions タブ → 失敗した run → 失敗したジョブ → 失敗したステップを開く。ログはステップ単位で畳まれているので、赤いステップだけ広げる。
  2. エラーの最後の数行に答えがあることが多い（コマンドのエラーは末尾に出る）。
  3. よくある原因トップ3：
    • YAML のインデント崩れ ― 「workflow file issue」でそもそも実行されない。エディタの YAML 表示で確認。
    • 権限不足 ― bot の push が 403 になる → permissions: contents: write の付け忘れ。
    • パス違い ― 「ファイルが無い」系。手元と違い、ランナーは毎回まっさらな環境＋作業フォルダはリポジトリ直下、という前提で見直す。
  4. 直したら、失敗した run の「Re-run jobs」で再実行できる（新しい push は不要）。
やってみる：hello.yml の echo をわざと存在しないコマンドに変えて失敗させ、ログから原因を特定して直す。この「壊して直す」一往復が一番の練習。

レッスン14：役割分担と次の一歩

ゴール：学んだ型を他の作業にも広げる見通しを持つ。
  • 手元（NixOS）：書く・試す・コミットする場所。重い処理や対話的な作業はここ。
  • PR：変更の関所と履歴書。どんな小さな変更でも、ブランチ＋PR＋スカッシュマージを型にする。
  • Actions：「push のたびにやる定型作業」の置き場。index 生成の次は、たとえば「リンク切れチェック」「ファイル名の命名規則チェック」などが候補。
  • 余力が出たら：Issue を自分の TODO 置き場にする（PR と Issue を紐付けると履歴がさらに追いやすい）、Release / タグで節目を付ける、くらいが次の階段。

全部を一度にやらないこと。型は「PR で入れる→チェックが付く→自動作業が増える」の順で、1つずつ増やすのが続くコツ。

付録B ― フラッシュカード

タップ／クリックで答えが出る。

Q. ソロ開発で PR を使う一番の実利は？（タップで答え）
A. main に入る前の「関所」。差分レビューと自動チェックで事故を止められ、変更理由の履歴書にもなる。
Q. スカッシュマージとは？（タップで答え）
A. ブランチ内の複数のコミットを1つに潰してから main に取り込む方式。main の履歴がきれいに保てる。
Q. ブランチ保護で Required approvals を 0 にするのはなぜ？（タップで答え）
A. ソロでは承認者が自分しかおらず儀式になるだけだから。「PR 経由でないと入れない」こと自体が本体。
Q. workflow_dispatch とは？（タップで答え）
A. ワークフローの手動実行トリガー。Actions タブに「Run workflow」ボタンが出る。試し運転に最適。
Q. fetch-depth: 0 が必要なのはどんなとき？（タップで答え）
A. ワークフロー内で git log など履歴を使うとき。初期設定は最新1件しか取得しない。make_index.sh v2 の日付がその例。
Q. bot のコミットが Actions を無限ループさせるのを防ぐ手は？（タップで答え）
A. paths で生成物（index.html）を対象から外す（'!html/index.html'）、生成物に変化が無いときはコミットしない、の二重構え。
Q. Actions の失敗調査、最初に見る場所は？（タップで答え）
A. 失敗した run → ジョブ → ステップのログ、その末尾数行。原因トップ3は YAML のインデント、権限、パス違い。
Q. actions/checkout の役割は？（タップで答え）
A. リポジトリのコードをランナー（仮想マシン）に持ってくる部品。ほぼ全てのワークフローの最初のステップに置く。
